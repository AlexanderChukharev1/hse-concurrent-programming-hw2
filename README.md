# Пул соединений

## 1. Замок и условия

`ReentrantLock lock` защищает настройки, коллекции `idle`, `borrowed`,
`waiting`, счётчики `creating`, `closing`, флаг `stopped` и изменяемое
состояние внутренних объектов.

| Условие | Кто ждёт | Кто и когда будит |
|---|---|---|
| `Waiter.ready` | Один ожидающий `borrow` | `dispatch` при назначении соединения или места либо обнаружении таймаута; `shutdown` при остановке |
| `schedule` | Поток очистки | Выдача, возврат, `resize` и `shutdown` для пересмотра ожидания очистки |
| `returned` | `shutdown` в пределах `grace` | Возврат последнего выданного соединения |
| `closed` | `shutdown` | Завершение последнего физического закрытия |

Ожидания проверяют состояние в циклах. Очередь обслуживается по порядку.
Соединение или место назначается до сигнала, поэтому новый вызов
не может перехватить ресурс ожидающего.

## 2. Учёт соединений вне замка

Под замком соблюдается:

```text
total = idle.size() + borrowed.size() + creating
```

Перед вызовом фабрики под замком проверяется наличие места и увеличивается
`creating`. Фабрика работает вне замка. Затем под замком резерв заменяется
выданным соединением либо освобождается при ошибке.

Перед физическим закрытием соединение исключается из учёта под замком
и увеличивается `closing`. `RawConnection.close()` выполняется вне замка,
после чего в `finally` под замком уменьшается `closing`.

Поэтому медленные операции не удерживают замок, а создание заранее
учитывается в `total`. Счётчик `closing` позволяет `shutdown` дождаться
уже начатых закрытий.

## 3. Отсутствие внутренней взаимоблокировки

Замок один. Ожидание на `Condition` освобождает его.
Фабрика, физическое закрытие и `join()` выполняются без замка.
Цикл ожидания внутренних замков возникнуть не может.

## 4. Зависание приложения

В `PoolStarvationTest` три потока при `maxSize = 3` берут по соединению,
встречаются на барьере и, удерживая первое, запрашивают второе
с минутным таймаутом.

Дамп снят командой `jcmd 31196 Thread.print`.
Фрагменты дампа; `...` обозначает пропуски:

```text

...

...

"starvation-request-2" ...
   java.lang.Thread.State: TIMED_WAITING (parking)
...
   at edu.hse.concurrency.pool.ConnectionPoolImpl.borrow(ConnectionPoolImpl.java:64)
   at edu.hse.concurrency.pool.PoolStarvationTest.lambda$allRequestsWaitForSecondConnection$1(PoolStarvationTest.java:40)
...

"starvation-request-3" ...
   java.lang.Thread.State: TIMED_WAITING (parking)
...
   at edu.hse.concurrency.pool.ConnectionPoolImpl.borrow(ConnectionPoolImpl.java:64)
   at edu.hse.concurrency.pool.PoolStarvationTest.lambda$allRequestsWaitForSecondConnection$1(PoolStarvationTest.java:40)
```

Каждый поток удерживает своё первое соединение и ждёт возврата соединения
одним из двух остальных потоков. Все они ожидают второе соединение,
поэтому никто не доходит до возврата первого.

JVM не сообщает `Found one Java-level deadlock`: она обнаруживает циклы
владения мониторами и ownable synchronizers. Здесь ожидаются ресурсы
приложения, а замок пула освобождён при ожидании на `Condition`.
Без вмешательства ожидание закончится по минутному таймауту.

Для `T >= 1` потоков, каждому из которых одновременно нужно `C >= 1`
соединений:

```text
maxSize_min = T * (C - 1) + 1
```

**Почему меньше нельзя.** При размере не больше `T * (C - 1)` можно
распределить все соединения так, чтобы каждый поток удерживал меньше `C`.
Тогда свободных соединений нет, а завершиться никто не может.
При `C = 1` минимальный допустимый размер равен 1.

**Почему достаточно.** Пока никто не набрал `C`, потоки вместе удерживают
не больше `T * (C - 1)` соединений. Поэтому остаётся свободное соединение
или место для создания. Выдача продолжается, пока один поток не получит
все `C`, завершится и вернёт ресурсы. Рассуждение повторяется для остальных.
Предполагается, что фабрика успешно завершается, а запрос после получения
всех соединений заканчивает работу и возвращает их.

Тест `minimalPoolLetsEveryRequestFinish` проверяет завершение всех потоков
при `T = 6`, `C = 1, 2, 3, 4` и размерах пула `1, 7, 13, 19`.
